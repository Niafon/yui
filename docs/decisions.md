## ADR-015. Лицензия: Apache-2.0

Файлы `LICENSE`, `NOTICE`.

Выбрана из-за явной патентной оговорки (§3) — для проекта с плагинами и
сторонними интеграциями это важнее, чем copyleft. Совпадает с лицензией
большинства моделей, которые мы используем (Qwen, Voxtral, CosyVoice).

**Следствия, о которых нужно помнить:**

- Каждый файл-контрибуция должен нести заголовок Apache. Добавлять при первом
  публичном релизе, не сейчас.
- **Live2D Cubism SDK не Apache и не совместим автоматически.** SDK имеет
  собственные коммерческие условия. В репозитории нет ни SDK, ни моделей;
  `desktop/src/live2d.ts` — интерфейс с заглушкой. Перед публикацией с Live2D
  нужно отдельно прочитать условия Cubism.
- **Parakeet под CC-BY-4.0** — требует указания авторства при распространении.
  Учтено в `NOTICE`.

## ADR-016. Целевая конфигурация: RTX 3080 10 ГБ

10 ГБ VRAM — жёсткий бюджет, и его делят четыре модели сразу. Это главное
ограничение всей системы, поэтому распределение зафиксировано явно:

| Компонент | Где исполняется | VRAM | Обоснование |
|---|---|---|---|
| LLM | GPU | ~6.0–6.5 ГБ | основной потребитель, остаётся резидентным |
| STT | CPU (ONNX INT8) | 0 | Parakeet/Nemotron специально быстрые на CPU |
| TTS | GPU | ~1.5–2 ГБ | нужен низкий latency, CPU-фолбэк есть |
| Embeddings | CPU | 0 | вызывается редко и вне латентного пути |
| Vision | GPU по требованию | ~2–3 ГБ | загружается только на кадр, потом выгружается |
| Резерв под контекст и всплески | | ~1 ГБ | |

**Ключевое следствие:** STT и embeddings уходят на CPU намеренно. Это
освобождает VRAM для LLM и снимает риск R-03 (конкуренция за память), не
ухудшая задержку — современные ASR-модели на CPU работают быстрее реального
времени.

Vision-воркер выгружает модель после простоя (`unload_after_seconds`), потому
что одновременно держать LLM + vision в 10 ГБ нельзя.

## ADR-017. Конкретные модели первой сборки (закрывает TBD-07)

Проверено по состоянию на 04.08.2026. Ландшафт меняется быстро — **перед
установкой проверьте, не вышло ли новее**.

### LLM: Qwen 3.5 9B (Q4_K_M), запасной — Qwen 3 14B (Q4_K_M)

- Apache-2.0, 201 язык с сильным русским, 262K контекста, hybrid thinking mode.
- 9B в Q4 занимает около 5–6 ГБ и оставляет место под контекст — на 10 ГБ это
  рабочий вариант, а не «влезает впритык».
- 14B Q4 (~9 ГБ) помещается, но не оставляет места vision-модели. Держать как
  «тяжёлый режим» для сложных запросов, не как основной.
- Альтернатива: Gemma 4 — сильнее в мультимодальности, но практичный размер
  (26B MoE) требует 16 ГБ. Не наш случай.

### STT: Parakeet TDT 0.6B v3 (CPU), запасной — Voxtral Realtime Q4

- Parakeet: 600M, INT8 ONNX ~630 МБ, 25 языков включая русский, WER ~6.3% на
  Open ASR Leaderboard, работает быстрее реального времени на CPU. Лицензия
  CC-BY-4.0 — требует атрибуции.
- Voxtral Realtime (Mistral, Apache-2.0, 4B, Q4 ~2.5 ГБ) — **нативный
  стриминг** и 13 языков включая русский, WER ниже Whisper. Берём, когда
  дойдём до partial-транскриптов, если Parakeet не даст нужного стриминга.
- GigaAM — русскоязычная специализированная модель, стоит померить на своём
  голосе: для одного пользователя специализация может выиграть у универсальной.
- Whisper large-v3-turbo остаётся эталоном для сравнения, но на CPU он
  медленнее, а на GPU отнимает память у LLM.

### TTS: CosyVoice2-0.5B, запасной — Silero (RU) / Piper

- CosyVoice2: ~150 мс до первого пакета в стриминге, 9 языков включая русский,
  кросс-язычное клонирование голоса из короткого образца, 0.5B — влезает
  рядом с LLM.
- Для образа компаньона клонирование важно: голос — часть личности, а не
  случайный пресет.
- Silero и Piper — CPU-фолбэк, если GPU занят или для «тихого» режима.
- Chatterbox Multilingual (MIT) звучит лучше всех в слепых тестах, но просит
  4–6 ГБ — не помещается вместе с LLM на 10 ГБ.

### Embeddings: bge-m3 (CPU), 1024 измерения

> Исторический профиль v0.2; для local mode заменён Qwen3-Embedding-0.6B 256d в ADR-037.

- Сильный русский, длинный контекст, широко поддержан. Размерность 1024
  зафиксирована в схеме (`vector(1024)`).
- Смена модели не теряет память: индекс перестраивается (MEM-004).

### Vision: Qwen3-VL 4B (Q4), загружается по требованию

- Совместим по токенизатору и стилю промптов с основной LLM.
- OCR отдельным лёгким движком, а не VLM: дешевле и точнее на тексте.

**Что нужно померить перед фиксацией** — раздел «Бенчмарк» ниже.

## ADR-018. Semantic index: pgvector + HNSW (закрывает TBD-06)

> Историческое решение v0.2; для локального режима заменено ADR-037.

Миграция `0002_pgvector.sql`.

- pgvector с HNSW-индексом; `vector(1024)`, косинусная метрика.
- Для персонального компаньона реальный объём — десятки, максимум сотни тысяч
  векторов. pgvector на таком масштабе отдаёт результат за единицы
  миллисекунд; узкое место — генерация эмбеддинга, а не поиск.
- **Порог перехода зафиксирован:** если векторов станет больше 5 млн или p95
  поиска превысит 50 мс — добавляем `pgvectorscale` (StreamingDiskANN,
  дисковый индекс, не требует держать всё в памяти). Это дополнение к
  pgvector, а не замена: SQL не меняется.
- Специализированные базы (Qdrant, Milvus) выигрывают на 10M+ векторов и
  высокой конкурентности. Для одного пользователя это лишний сервис в
  установке — прямое противоречие NFR-007.
- Источником истины остаются строки `memory_items`. Вектор — производная,
  удаляется и перестраивается.

## ADR-020. Wake word: три режима на выбор пользователя (закрывает TBD-19)

`config.Voice.WakeWord.Mode`:

| Режим | Что происходит | Цена |
|---|---|---|
| `off` | только кнопка / открытая сессия | ноль фона |
| `device` | детектор на телефоне, на ПК уходит только речь после активации | экономит батарею и трафик, задержка выше |
| `core` | телефон стримит аудио постоянно, детектор на ПК | ниже задержка, выше расход батареи и трафика |

Умолчание — `device`: батарея телефона важнее сотни миллисекунд.
Переключение — в настройках, без пересборки.

## ADR-021. Barge-in: режимы `off / button / wake_word / any_speech` (закрывает TBD-11)

`config.Voice.BargeIn.Mode`. Швы были готовы заранее: `Manager.CancelTurn`,
отменяемый по контексту `TTS.Synthesize`.

- `button` — умолчание, работает без эхоподавления.
- `wake_word` — прервать можно только обращением по имени; компромисс между
  удобством и ложными срабатываниями.

  игнорирует срабатывания в первые `min_speech_ms` после начала синтеза.

## ADR-024. Восстановление ключа по паролю (закрывает TBD-02, TBD-03)

Пакет `core/internal/crypto`.

Схема — envelope encryption, стандарт для PostgreSQL, у которого нет
собственного TDE:

```
пароль ──Argon2id──▶ KEK ──AES-256-GCM──▶ обёрнутый DEK (в keyfile)
                                              │
                          DEK ──AES-256-GCM──▶ данные (поля и медиа)
```

- **DEK генерируется один раз** и никогда не выводится из пароля напрямую:
  поэтому смена пароля перезаворачивает ключ за миллисекунды и не требует
  перешифровки памяти.
- **Два способа открыть DEK:** пароль или recovery-файл (тот же DEK,
  завёрнутый случайным 256-битным ключом, который печатается один раз при
  инициализации). Потеря пароля не означает потерю памяти — это и было
  требованием.
- Argon2id, параметры: 3 прохода, 64 МБ, parallelism 4 (текущая рекомендация
  OWASP). Хранятся в заголовке keyfile, чтобы их можно было поднять позже без
  потери совместимости.
- AES-256-GCM, случайный nonce на каждую операцию, счётчик операций в
  заголовке — ротация до приближения к 2³² (nonce collision).

## ADR-025. Шифрование на Windows: два уровня (закрывает TBD-05, TBD-12)

Проверено: **в PostgreSQL нет встроенного TDE** (подтверждено документацией
PostgreSQL 18 и обзорами 2026 года). Поэтому:

1. **Том с БД — BitLocker.** Защищает от кражи диска, ничего не стоит по
   производительности, настраивается вне приложения. Установщик проверяет и
   предупреждает, если том не зашифрован.
2. **Чувствительные поля и все медиа — на уровне приложения** (ADR-024).
   Защищает даже от того, кто получил доступ к работающей БД. Шифруются:
   `sensitivity IN (sensitive, medical, biometric)`, медиафайлы целиком,
   секреты провайдеров.

Отклонено: `pgcrypto` (ключ попадает в SQL и в логи запросов), `pg_tde`
(молодое расширение, усложняет установку), форки с TDE (несовместимо с
требованием «одна установка без администратора БД»).

**Аудит (TBD-04):** хранится 180 дней, отключить отдельные категории нельзя —
журнал безопасности, который можно выборочно отключить, бесполезен. Можно
удалить весь журнал целиком, с записью об удалении.

## ADR-026. Инструменты MVP: полный набор низкого и среднего риска (закрывает TBD-13)

Пакет `core/internal/tools`. Реализованы: время и дата, поиск по памяти,
напоминания, таймеры, заметки, задачи, календарь (чтение), управление
музыкой, погода, открытие ссылки.

Модель обращения к инструменту проходит: валидацию схемы → capability →
permission → оценку риска → подтверждение (если нужно) → выполнение → аудит.
Уровни риска и требуемые факторы — по таблице SRS 16.5, без исключений.

**Чего нет намеренно:** отправка сообщений от имени владельца, звонки,
платежи, удаление файлов, выполнение произвольных команд ОС. Экстренного
вызова нет вовсе (SEC-013) — отсутствие кода и есть выполнение требования.

## ADR-028. Визуальные события: режимы вместо одного порога (закрывает TBD-10)

`config.Vision.EventMode`: `off / manual / motion / periodic / smart`.

- `manual` — умолчание: кадр уходит в модель только по просьбе.
- `motion` — дешёвый детектор движения по разнице кадров, порог настраивается.
- `periodic` — снимок раз в N секунд при открытой сессии.
- `smart` — движение плюс минимальный интервал плюс дедупликация похожих
  кадров; самый дорогой.

Лучший режим определяется тестами на реальном использовании — поэтому их
четыре, а не один зашитый порог.

---

## ADR-029. Удалённый доступ: три режима (закрывает TBD-15)

`config.Remote.Mode`: `lan / vpn / relay`.

- `lan` — умолчание, ядро слушает только локальную сеть.
- `vpn` — рекомендуемый способ для доступа извне (WireGuard/Tailscale);
  ядро о VPN ничего не знает, что и хорошо.
- `relay` — собственный сервер-ретранслятор. **Не реализован**: требует
  zero-knowledge архитектуры и отдельной threat model. Режим объявлен в
  конфиге, чтобы клиенты уже умели его отображать, но ядро отказывается
  стартовать с `relay`, пока не появится реализация. Явный отказ лучше
  видимости защиты, которой нет.

# Бенчмарк: что померить на RTX 3080 перед фиксацией моделей

Порядок важен — каждый шаг отсекает варианты для следующего.

1. **VRAM под нагрузкой.** Загрузить LLM + TTS + vision одновременно и
   посмотреть пик. Если пик выше 9.5 ГБ — vision уходит в режим «загрузка по
   требованию с выгрузкой» (уже реализовано в конфиге воркера).
2. **Задержка по этапам.** Ядро уже пишет `latency_ms` в кадр `turn.done`;
   нужен разрез по этапам: STT → context → первый токен → первый аудиочанк.
   Цель по SRS — 1–2 с до начала ответа. Наибольший подозреваемый — время до
   первого токена на 9B в Q4.
3. **STT на своём голосе, по-русски.** Parakeet против GigaAM против Voxtral.
   Читать не текст, а обычную речь с паузами — леaderboard-датасеты этого не
   показывают.
4. **TTS: время до первого пакета.** CosyVoice2 обещает ~150 мс; проверить на
   коротких фразах, потому что именно они звучат в диалоге.
5. **Долгая сессия.** 30 минут непрерывно: утечки памяти, деградация
   задержки, поведение при переключении наушников (AC-03, NFR-002).
6. **Только после этого** фиксировать модели в `yui.config.json`.

# Обновления от 28.08.2026 (ADR-032 … 036)

За три недели вышли Go 1.27, обновления pgvector закрепились в 0.8.x, и —
важнее всего — сместился модельный ландшафт. Ниже только то, что меняет код,
а не то, что просто вышло.

## ADR-032. Go 1.27 и обращение с ключевым материалом

`core/go.mod`, `internal/crypto/`.

Апгрейд с 1.22 сразу на 1.27. Четыре причины, каждая попадает в наше слабое
место, а не в общий список улучшений:

| Что | Почему это про нас |
|---|---|
| **Green Tea GC** (по умолчанию с 1.26) | −10…40% накладных расходов сборщика. Ядро живёт неделями и держит долгие сессии; это ровно тот профиль, где выигрыш заметен |
| **encoding/json v2** под капотом `encoding/json` | JSON у нас на горячем пути: каждый кадр WebSocket и каждый вызов воркера. Разбор заметно быстрее, менять код не нужно |
| **Профиль `goroutineleak`** (GA в 1.27) | Основной режим отказа компаньона — не падение, а горутина сокета, которая не вернулась после закрытия сессии. См. ADR-034 |
| **`testing/synctest`** | Планировщик наконец тестируется детерминированно. См. ниже |
| **`crypto/tls` MLKEM1024** | См. ADR-035 |

**Ключевой материал теперь затирается явно.** `zero()` перезаписывает DEK,
KEK и пароль сразу после использования, а `Scrubbed()` оборачивает участки,
работающие с сырыми байтами ключа. Под тегом `-tags yuisecret` `Scrubbed`
использует `runtime/secret` из Go 1.26/1.27, который стирает и копии на стеке
и в регистрах. Тег опциональный, потому что пакет пришёл как эксперимент, а
чистый checkout обязан собираться без флагов.

**Заодно исправлена настоящая ошибка.** Идентификатор ключа выводился из
первых шести байт самого DEK — то есть 48 бит ключа лежали открытым текстом в
файле ключа и рядом с каждой зашифрованной записью. Теперь это независимое
случайное значение. Регрессия закрыта тестом.

### Тесты планировщика на synctest

Правило «фоновая рефлексия уступает живому разговору» (NFR-006, AC-14) до сих
пор не было покрыто: проверить его можно было только через `sleep`, а значит
медленно и нестабильно. В `synctest` время виртуальное — задание с интервалом
в 15 минут отрабатывает за микросекунды. Пять тестов закрывают: соблюдение
интервала, подавление при активной сессии, **отмену уже запущенного задания**,
изоляцию падающего задания от соседей и выключенный планировщик.

## ADR-033. pgvector 0.8: halfvec и итеративные сканы

> Историческое решение v0.2; для локального режима заменено ADR-037.

`core/migrations/0004_vector_tuning.sql`, `store/postgres`.

Два изменения, и оба попадают ровно в форму нашего запроса.

**Итеративные сканы решают проблему, которая у нас была.** Мы всегда сначала
фильтруем — по пространству памяти, по «живости», иногда по категории — и
только потом сортируем по расстоянию. Это классический случай
переотфильтровывания: HNSW отдаёт свои `ef_search` кандидатов, `WHERE`
выбрасывает почти всех, и запрос возвращает слишком мало строк или ноль.
Редко используемое пространство памяти могло молча не находиться вообще.
`hnsw.iterative_scan = relaxed_order` заставляет pgvector добирать кандидатов,
пока фильтр не будет удовлетворён. Порядок при этом приблизительный — нам
всё равно, потому что `Rank` пересортирует результат своей формулой.

Настройка ставится через `SET LOCAL` внутри транзакции, а не на уровне
сессии: сессионная настройка утекла бы на все остальные запросы через тот же
пул соединений.

**halfvec** (float16) вдвое уменьшает индекс и резидентную память при
пренебрежимой потере полноты на 1024 измерениях. На машине, где LLM уже
забрала большую часть бюджета, это разница между индексом, который остаётся
горячим, и индексом, который не остаётся.

Колонка полной точности сохранена на один релиз ради отката; миграция 0005
её удалит.

## ADR-034. Диагностика долгоживущего процесса

`internal/api/debug.go`, `config.Diagnostics`.

Профиль `goroutineleak` находит именно тот класс утечек, который у нас
возможен: горутина, заблокированная на канале, который никто уже не может
просигналить. Фоновое задание раз в полчаса считает такие горутины и
предупреждает, когда их становится больше 25 — с указанием, где смотреть
профиль.

**Вся отладочная поверхность привязана к loopback и выключена по умолчанию.**
Дамп горутин персонального ассистента — сам по себе чувствительные данные:
имена функций и форма стека описывают, чем владелец занимался. Удалённому
запросу отдаётся 404, а не 403: незачем сообщать, что эндпоинт существует.

Заодно на HTTP-сервере выставлены `MaxHeaderBytes` и новое в 1.27
`MaxHeaderValueCount`. Ядро слушает домашнюю сеть, где скомпрометированное
умное устройство — более реалистичный противник, чем интернет.

## ADR-035. Постквантовый обмен ключами

`internal/api/tls.go`.

База компаньона — это десятилетие частной жизни одного человека. Для такого
хранилища «собери сейчас, расшифруй потом» перестаёт быть теоретической
угрозой: трафик, записанный в домашней сети сегодня, можно открыть, когда
квантовые атаки на классический обмен ключами станут практичными, и
содержимое всё ещё будет личным.

Go по умолчанию использует гибридный X25519MLKEM768 с версии 1.24; мы
запрашиваем гибрид явно, а не наследуем то, что окажется умолчанием.
Классические кривые остаются в списке — гибридные схемы гибридны именно
затем, чтобы изъян в постквантовой половине не сделал хуже.

Билеты сессий выключены: ядро не публичный веб-сервер, и ключ билетов, который
некому ротировать, — лишняя цель.

## ADR-036. Зрение через мультимодальную LLM

`internal/provider/vision_openai.go`.

Это самое существенное из вышедшего. **Qwen 3.5 несёт зрение в базовых
весах** — включая 9B, который мы уже держим резидентным. Значит, вопрос
больше не «какой VLM выбрать», а «нужна ли вторая модель вообще».

Что это меняет на 10 ГБ:

- освобождается 2–3 ГБ VRAM;
- исчезает загрузка и выгрузка vision-модели — самая непредсказуемая часть
  системы, и вместе с ней исчезает риск R-03 в этой части;
- пропадает задержка первого кадра: модель уже в памяти.

Компромисс честный и назван в коде: выделенный VLM обычно точнее на OCR и
мелких деталях. Поэтому это **драйвер, а не замена** — воркер остался,
переключение одной строкой в `default_providers`. В примере конфигурации
vision-воркер переведён в `autostart: false`.

Ответ модели разделяется на описание сцены и распознанный текст: текст на
экране часто приватнее, чем сама сцена, и хранить их с разной
чувствительностью правильнее.

Промпт зрения содержит явное ограничение: описывать наблюдаемое, а не строить
выводы о личности, настроении или намерениях людей в кадре. Это не вежливость,
а прямое следствие VIS-008 и риска R-12.

## Что проверено и осталось без изменений

> Раздел фиксирует состояние ADR-036 на 28.08.2026; storage-пункт ниже заменён ADR-037.

- **Qwen 3.5 9B Q4 остаётся основной моделью.** Вышли Qwen 3.6 (27B dense) и
  Gemma 4 (26B MoE), но оба нацелены на 16–24 ГБ. Для 10 ГБ 9B по-прежнему
  «рабочая лошадка».
- **Parakeet TDT 0.6B v3 на CPU** — выбор подтверждается. Voxtral Realtime
  (Apache-2.0, нативный стриминг, русский) остаётся первым кандидатом на
  замену, когда дойдём до partial-транскриптов.
- **CosyVoice2-0.5B** — без изменений. Chatterbox звучит лучше в слепых
  тестах, но просит 4–6 ГБ и не помещается рядом с LLM.
- **Tauri** — обновлён до 2.11 в `package.json`; API не менялся.
- **pgvector остаётся правильным выбором.** Порог перехода на pgvectorscale
  (>5 млн векторов или p95 >50 мс) не изменился; в 0.9.0 DiskANN научился
  `CREATE INDEX CONCURRENTLY`, что делает будущий переход безболезненным.

## Что стоит перепроверить при замерах

К плану замеров добавляются два пункта:

6. **Зрение через LLM против выделенного VLM.** Померить на своих кадрах:
   качество описания, точность OCR, время ответа. Если OCR критичен —
   вернуть `vision-worker`.
7. **Пик VRAM без vision-модели.** Он должен упасть на 2–3 ГБ, что открывает
   дорогу к Qwen 3 14B Q4 в качестве «тяжёлого режима» без вытеснения в
   разделяемую память.

## ADR-037. Embedded SQLite + FTS5 + exact semantic cache (2026-09-05)

**Статус:** принято. **Заменяет ADR-018, ADR-019 и ADR-033 для локального
single-user режима.** PostgreSQL backend остаётся только для совместимости и
экспорта старых установок.

После повторного обзора рынка storage/vector решений выбор изменён с
PostgreSQL + pgvector на embedded архитектуру:

- durable source of truth — один файл SQLite в WAL mode;
- lexical retrieval — FTS5/BM25 (`ORDER BY rank`);
- embedding хранится compact float32 BLOB с произвольной размерностью;
- при старте Core строит нормализованный in-process cache;
- semantic search — полный exact cosine scan, без ANN;
- semantic и FTS candidates объединяются существующим memory Rank;
- ANN является будущей оптимизацией, а не обязательной частью формата данных.

### Почему не Qdrant Edge сейчас

Qdrant Edge очень хорошо соответствует форме продукта (embedded, in-process,
без background service), но на момент решения официально имеет статус beta.
Он остаётся первым кандидатом на future large-corpus backend после стабилизации.

### Почему не SQLite Vec1 / sqlite-vec ANN сейчас

Vec1 0.7 уже интересен как компактный native ANN, но его online-update режим
ещё развивается. `sqlite-vec` имеет stable exact path, однако проект всё ещё
pre-1.0, а новая DiskANN/IVF ветка остаётся pre-release. Для authoritative
memory layer сейчас выгоднее опираться только на mature SQLite/FTS5 и держать
vector acceleration сменной derived-структурой.

### Почему exact scan

На масштабе личной памяти стоимость полного scan остаётся малой, а преимущества
существенны: 100% recall относительно cosine layer, нулевое обслуживание graph,
мгновенные insert/update/delete и простая диагностика. Cache хранит уже
L2-normalized vectors, поэтому каждый candidate требует только dot product.

Порог перехода на ANN **не фиксируется числом из чужого benchmark**. Он должен
появиться из локального теста p95 на целевой машине. Если exact semantic search
начинает занимать заметную долю TTFT, за `MemoryRepo.VectorSearch` добавляется
Qdrant Edge / Vec1 / HNSW / DiskANN backend без изменения storage schema.

### Embeddings

Default profile меняется с BGE-M3 1024d на Qwen3-Embedding-0.6B 256d MRL.
Размерность больше не зашита в SQL schema. Worker различает query/document:
для Qwen3 query используется named `query` prompt, документы кодируются без
него. Это одновременно уменьшает resident vector memory примерно в 4 раза
против 1024d float32 и позволяет использовать instruction-aware retrieval.

## ADR-038. Adaptive model/backend scheduler (2026-09-05)

**Статус:** принято.

Одна постоянно резидентная LLM конфликтует с основной продуктовой целью:
компаньон должен отвечать во время игры, IDE/рендера и при этом не создавать
заметные frametime spikes. Поэтому выбор модели и место inference становятся
runtime-решением, а не статической строкой `default_providers.llm`.

### Приоритет управления

1. provider, явно выбранный для session;
2. user model lock (`model_family`);
3. пользовательские resource/quality limits;
4. gaming/FPS guardrails;
5. сложность текущей задачи;
6. текущая CPU/GPU/RAM/VRAM нагрузка;
7. внутренний score scheduler.

Manual lock нельзя игнорировать. Если `qwen3.5-9b` имеет GPU и CPU profiles,
scheduler может менять backend, но не имеет права перейти на 4B. Если выбран
конкретный provider, даже backend фиксируется и ошибка показывается явно.

### Telemetry

Core опрашивает систему редко (`poll_interval_ms`, default 3000), чтобы сам
resource monitor не стал источником overhead. Windows CPU/RAM/foreground app
берутся напрямую через WinAPI. NVIDIA GPU utilization и VRAM — одним
`nvidia-smi` query. FPS/baseline FPS/frametime являются optional client
telemetry: overlay может прислать их в `POST /v1/inference/telemetry`.

### Selection

Каждый provider описывает `model_family`, `execution_backend`, относительный
`quality`, ожидаемые RAM/VRAM, `gaming_safe`, `auto_select` и optional
`worker_id`. Для gaming lightweight profiles получают бонус, а memory footprint
— дополнительный штраф. При превышении GPU utilization/VRAM reserve/FPS loss
GPU candidate отбрасывается до вызова модели.

### Residency

Опциональные llama.cpp servers регистрируются как Supervisor workers с
`autostart=false`. При выборе provider Model Manager cold-start'ит worker и
ждёт health endpoint. Если Auto-profile не установлен или не стартовал,
проверяется следующий ranked candidate. Cloud не является скрытым fallback.
Manual/explicit choice, наоборот, завершается видимой ошибкой.

### Почему не один Ollama process

OpenAI-compatible Ollama endpoint остаётся удобным default/fallback, но он не
даёт Core строгого контроля над CPU/GPU placement для каждого model profile.
Managed llama.cpp servers делают placement явным (`-ngl 0` CPU, GPU offload
для GPU profile) и потому используются, когда нужен гарантированный gaming
budget. Provider interface при этом не меняется.
