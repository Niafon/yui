# Yui Companion

Текущая версия проекта: **0.3.1**

Yui — это локальный AI-companion для ПК и других устройств пользователя. Главная идея проекта — не просто сделать ещё один чат с LLM, а построить постоянного персонального AI-ассистента, который живёт рядом с пользователем, понимает контекст происходящего на компьютере, умеет слышать голос, видеть экран, использовать локальные и облачные модели, обращаться к интернету и внешним инструментам, выполнять команды и при этом потреблять как можно меньше ресурсов.

Проект ориентирован прежде всего на Windows Desktop, но архитектура должна оставаться пригодной для мобильного клиента и удалённого управления через телефон.

## Основная цель

Yui должна ощущаться как постоянно доступный AI-компаньон уровня системного ассистента.

Пользователь может:

- говорить с Yui голосом;
- писать ей с ПК или телефона;
- попросить посмотреть на экран;
- попросить понять, что происходит в приложении или игре;
- попросить найти актуальную информацию в интернете;
- попросить выполнить действие через инструмент;
- получать ответ текстом или голосом;
- использовать Yui одновременно с играми и тяжёлыми приложениями;
- выбирать качество AI вручную либо позволить системе автоматически адаптироваться к доступным ресурсам.

Ключевой принцип проекта:

**AI должен подстраиваться под компьютер, а не компьютер под AI.**

Если пользователь играет, работает, рендерит видео или запускает тяжёлое приложение, Yui должна уменьшать собственное потребление ресурсов. Если ПК свободен, Yui может автоматически использовать более мощные модели и более качественные режимы.

---

# Пример целевого сценария

Пользователь играет в Dota 2 и говорит:

«Yui, посмотри, на каком я герое, какая сейчас минута и что мне лучше купить следующим предметом».

Yui должна:

1. Получить голос.
2. Преобразовать речь в текст.
3. Понять намерение пользователя.
4. Сделать скриншот игрового окна.
5. Определить героя, игровое время, предметы, золото и другой доступный контекст.
6. При необходимости обратиться к OpenDota, Dotabuff-подобным источникам, гайдам, текущей мете или веб-поиску.
7. Передать структурированные данные основной LLM.
8. Сформировать короткий полезный ответ.
9. Озвучить его.
10. Не вызвать заметного падения FPS или frametime spike.

В идеальном случае большая часть пайплайна выполняется только после запроса пользователя, а не непрерывно.

# Главные приоритеты проекта

Приоритеты должны соблюдаться примерно в таком порядке.

## 1. Минимальное влияние на основную работу компьютера

Это один из самых важных принципов Yui.

Во время игры или тяжёлой работы пользовательский процесс всегда важнее AI.

Приоритет ресурсов:

1. Игра / foreground-приложение.
2. Frametime и FPS.
3. Отзывчивость Windows.
4. Voice latency Yui.
5. Скорость генерации AI.

Yui не должна ради дополнительных 20–50 токенов в секунду создавать просадки FPS.

---

## 2. Максимальное качество при доступных ресурсах

Если компьютер свободен, Yui должна использовать максимально качественную доступную модель.

Например:

ПК свободен:
Qwen 9B на GPU.

ПК немного загружен:
Qwen 9B hybrid или CPU.

Идёт игра:
Qwen 4B CPU.

Очень высокая нагрузка:
маленькая модель или tool-only pipeline.

Таким образом качество является динамическим.

---

## 3. Пользователь всегда имеет более высокий приоритет, чем автоматика

Если пользователь вручную выбрал модель, Yui не должна самостоятельно заменить её другой моделью.

Например:

Model Lock = Qwen 9B.

Разрешено:

Qwen 9B GPU → Qwen 9B Hybrid → Qwen 9B CPU.

Не разрешено без согласия:

Qwen 9B → Qwen 4B.

Модель и execution backend — разные понятия.

---

## 4. Локальность и приватность

По возможности основные функции должны работать локально:

- LLM;
- speech-to-text;
- TTS;
- embeddings;
- vision;
- memory;
- routing.

Облако и интернет используются там, где это действительно повышает качество или необходимо для получения актуальной информации.

Не следует отправлять экран, голос и личные данные во внешние сервисы без необходимости.

---

## 5. Низкая задержка

Пользователь должен чувствовать, что Yui отвечает почти сразу.

Поэтому предпочтительны:

- streaming STT;
- streaming LLM generation;
- streaming TTS;
- preloaded hot-model;
- asynchronous tools;
- быстрый intent routing;
- tool-first подход;
- минимальный размер prompt;
- короткий контекст там, где длинный не нужен.

---

# Основная концепция архитектуры

Yui не должна быть монолитной моделью.

Это система нескольких специализированных AI-компонентов.

Пример:

```text
User
  │
  ├─ Voice
  ├─ Text
  ├─ Screenshot
  └─ Mobile
       │
       ▼
┌──────────────────────┐
│       Yui Core       │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│ Intent / Task Router │
└──────────┬───────────┘
           │
  ┌────────┼───────────────┐
  ▼        ▼               ▼
Tools     Vision           LLM
  │        │               │
  └────────┼───────────────┘
           ▼
       Response
           │
      ┌────┴────┐
      ▼         ▼
     Text      TTS
```

# Adaptive Inference Runtime

Начиная с версии 0.3.1 в Yui закладывается отдельная подсистема управления inference.

Основные компоненты:

- Model Registry;
- Resource Monitor;
- Task Classifier;
- Model Scheduler;
- Backend Scheduler;
- Model Manager;
- Worker Supervisor.

Scheduler должен учитывать одновременно:

- CPU usage;
- RAM usage;
- GPU utilization;
- VRAM usage;
- foreground process;
- наличие игры;
- температуру при необходимости;
- сложность запроса;
- тип задачи;
- текущие загруженные модели;
- пользовательские настройки;
- допустимое влияние на FPS;
- model lock;
- quality floor.

Результат работы scheduler — Inference Plan.

Пример:

```text
Task: game_build_advice
Complexity: medium

GPU: 96%
CPU: 42%
VRAM free: 1.8 GB
Foreground: dota2.exe

Decision:
Model: Qwen 3.5 4B
Backend: CPU
Vision: on demand
Reason: gaming profile + high GPU load
```

# Режимы работы AI

Yui должна поддерживать следующие режимы.

## Auto

Полный автоматический выбор модели и backend.

Scheduler сам определяет лучший вариант.

---

## Max Quality

Главный приоритет — качество.

Используется самая мощная доступная модель.

Ресурсные ограничения остаются только для защиты системы.

---

## Balanced

Баланс между качеством, latency и использованием ресурсов.

Рекомендуемый режим для большинства пользователей.

---

## Gaming

Приоритет игры.

Основные правила:

- минимальная нагрузка GPU;
- CPU inference предпочтительнее;
- ограниченное количество CPU threads;
- vision запускается только по запросу;
- небольшой context;
- низкий process priority;
- модели не должны занимать критически необходимую игре VRAM.

---

## Manual

Пользователь сам выбирает модель.

Scheduler может менять backend только в пределах разрешённых настроек.

---

# Model Lock

Model Lock имеет максимальный приоритет.

Пример:

```text
Preferred model: Qwen 3.5 9B
Model lock: ON
```

Yui может выбирать:

```text
9B CUDA
9B hybrid
9B CPU
```

но не может самостоятельно заменить её:

```text
9B → 4B
```

---

# Quality Floor

Пользователь может разрешить автоматическую смену моделей, но определить минимально допустимый уровень.

Пример:

```text
Preferred:
Qwen 9B

Auto downgrade:
Enabled

Minimum:
Qwen 4B
```

Scheduler может использовать 9B или 4B, но никогда 2B.

---

# Модельный стек

Конкретные модели должны легко заменяться.

Архитектура не должна быть привязана к Qwen.

На текущем этапе основной вариант:

### Main high-quality model

Qwen 3.5 9B.

Используется:

- сложный reasoning;
- программирование;
- глубокий анализ;
- сложные пользовательские запросы;
- desktop idle mode.

---

### Main lightweight model

Qwen 3.5 4B.

Используется:

- Gaming Mode;
- быстрый диалог;
- tool-assisted задачи;
- ситуации с ограниченными ресурсами.

---

### Tiny model

Примерно 0.8B–2B.

Не обязательно использовать для обычного общения.

Основные задачи:

- classification;
- intent detection;
- routing;
- простые структурированные команды;
- классификация сложности запроса.

При возможности часть этих задач лучше выполнять вообще без LLM.

---

# Vision

Vision не должна постоянно анализировать весь экран.

Это слишком дорого и в большинстве случаев бессмысленно.

Основной принцип:

**event-driven vision.**

Например:

пользователь сказал «посмотри на экран» → захватить кадр → проанализировать → удалить/освободить ресурсы.

Для игровых сценариев желательно иметь два пути.

Fast path:

```text
Screenshot
↓
Crop HUD
↓
OCR / CV / template recognition
↓
Structured data
```

Smart path:

```text
Screenshot
↓
Vision model
↓
Semantic understanding
```

Smart path используется только когда простого CV недостаточно.

---

# Speech-to-Text

STT должен быть максимально лёгким.

Возможные реализации:

- whisper.cpp;
- faster-whisper;
- другие локальные модели.

Предпочтительные режимы:

push-to-talk или wake-word.

Не нужно непрерывно запускать тяжёлую transcription-модель, если пользователь ничего не говорит.

---

# TTS

Ответы Yui должны по возможности озвучиваться.

Приоритеты TTS:

1. низкая задержка;
2. естественный голос;
3. локальная работа;
4. streaming;
5. низкое потребление ресурсов.

Можно использовать отдельный лёгкий TTS worker.

---

# Tool-first philosophy

Очень важный принцип проекта:

**не использовать LLM там, где задачу надёжнее и дешевле решает инструмент.**

Примеры.

«Который час?»

Не нужен LLM.

«Запусти Spotify».

Не нужен большой LLM.

«Какая загрузка GPU?»

System API.

«Какой сейчас winrate героя?»

API / web data.

«Что происходит на экране?»

Vision.

«Почему архитектура этого backend плохая?»

LLM.

Это снижает:

- latency;
- энергопотребление;
- количество hallucinations;
- RAM/VRAM;
- стоимость облачных запросов;
- размер контекста.

---

# Работа с интернетом

Интернет является инструментом, а не основной моделью.

Приоритет получения данных:

```text
Local API / structured API
        ↓
Official API
        ↓
Search
        ↓
Browser / scraping
```

Если информация доступна как JSON, не следует открывать полноценный браузер.

Пример Dota:

OpenDota API предпочтительнее ручного просмотра Dotabuff.

Web/browser используется для:

- свежих патчноутов;
- новостей;
- гайдов;
- сайтов без API;
- пользовательского поиска.

---

# Контекст пользователя

Yui должна постепенно становиться персонализированным companion.

Нужны различные виды памяти:

### Session memory

Текущий разговор.

### Short-term memory

Недавние действия, приложения и контекст.

### Long-term memory

Устойчивые предпочтения пользователя.

### Semantic memory

Embeddings / vector retrieval.

### Structured memory

Например:

```text
preferred_language = ru
preferred_code_language = Go
gaming_mode_max_fps_loss = 2%
favorite_games = [...]
```

Однако память должна быть контролируемой пользователем.

---

# Desktop Companion

Desktop-приложение — основной клиент.

Оно должно работать как:

- tray application;
- overlay;
- голосовой assistant;
- AI chat;
- settings interface;
- runtime monitor.

Желательно минимальное потребление RAM и CPU в idle.

---

# Mobile Client

Телефон должен выступать вторым интерфейсом к тому же Yui Core.

Пример:

ПК дома включён.

Пользователь пишет с телефона.

Yui использует мощность домашнего ПК и локальные модели.

Настройка модели с телефона должна менять именно общий runtime Core.

Например пользователь с телефона выбирает:

Max Quality → Qwen 9B.

Если ПК свободен, модель запускается на GPU.

---

# Resource Monitor

Необходимо постоянно, но очень дёшево получать:

- CPU utilization;
- RAM usage;
- GPU utilization;
- VRAM;
- foreground process;
- список тяжёлых процессов.

Для Windows желательно использовать нативные API.

Не следует постоянно запускать PowerShell-команды.

Для NVIDIA допустимо использование NVML или аналогичного лёгкого механизма.

---

# Game Detection

Yui должна понимать, когда запущена игра.

Пример:

```text
dota2.exe
cs2.exe
RobloxPlayerBeta.exe
```

При обнаружении игры scheduler может автоматически активировать Gaming Mode.

Однако пользовательские настройки имеют больший приоритет.

---

# Dynamic backend selection

Модель и место её выполнения выбираются независимо.

Возможные backend:

- CUDA;
- CPU;
- hybrid CPU/GPU;
- в будущем DirectML/Vulkan;
- remote;
- cloud.

Например одна и та же Qwen 9B:

```text
Desktop idle
→ 100% GPU

Medium load
→ partial GPU offload

Gaming
→ CPU
```

---

# Hot и Cold Models

Все модели не должны постоянно находиться в VRAM.

Модели имеют состояния:

- unloaded;
- disk;
- mmap;
- RAM;
- VRAM;
- active.

Например:

```text
RAM:
Qwen 4B READY
Qwen 9B READY

VRAM:
только активная модель
```

При достаточном количестве RAM веса можно держать доступными через mmap.

---

# Model Registry

Каждая модель должна описываться конфигурацией, а не хардкодиться.

Пример полей:

```text
id
family
name
parameter_count
quantization
model_path
vision_support
tool_support
context_length
estimated_ram
estimated_vram
supported_backends
quality_score
speed_score
priority
```

Это позволит через несколько месяцев просто заменить Qwen новой моделью.

---

# Task Classification

До запуска основной модели Yui должна определить тип задачи.

Примеры:

```text
COMMAND
SEARCH
CHAT
CODING
REASONING
SCREEN_ANALYSIS
GAME_ASSIST
VISION
MEMORY
SYSTEM_CONTROL
```

Также определяется complexity:

```text
trivial
low
medium
high
very_high
```

После этого scheduler принимает решение.

Пользователь:

«Открой Telegram».

```text
Task: COMMAND
Complexity: trivial
```

Пользователь:

«Что мне собирать дальше на Juggernaut?»

«Проведи глубокий review архитектуры моего проекта».

```text
Task: REASONING
Complexity: very_high

→ Qwen 9B
```

# Главная продуктовая философия

Yui не должна пытаться заменить всё одной гигантской моделью.

Её преимущество должно заключаться в грамотной orchestration.

То есть:

маленькая модель + правильный tool + правильный контекст

может быть лучше:

огромная модель без инструментов.

Качество продукта определяется не только benchmark LLM, но всем pipeline:

```text
Voice
+
Context
+
Vision
+
Memory
+
Tools
+
Internet
+
Routing
+
LLM
+
TTS
```

# Производительность

Для каждого нового компонента следует задавать вопрос:

«Как это повлияет на пользователя, если одновременно запущена игра?»

Idle Yui должна потреблять почти нулевые ресурсы.

Целевой подход:

- никаких постоянных vision inference;
- никаких постоянных больших LLM;
- никаких polling loops с высокой частотой;
- минимум background threads;
- event-driven архитектура;
- lazy load;
- mmap;
- worker sleeping;
- model unloading;
- кэширование.

---

# Игровой режим

Gaming Mode является одной из ключевых особенностей проекта.

Цель:

AI companion, которым реально можно пользоваться во время игры.

Yui должна автоматически защищать:

- FPS;
- frametime;
- VRAM;
- CPU latency.

При необходимости качество ответа снижается раньше, чем качество игры.

---

# Технологический принцип

Backend должен оставаться максимально быстрым и простым.

Не следует использовать тяжёлый framework только ради удобства, если это увеличивает:

- latency;
- RAM;
- количество процессов;
- сложность deployment.

Предпочтительны лёгкие native-компоненты и отдельные worker-процессы.

---

# Надёжность

Если один AI-компонент падает, весь companion не должен падать.

Пример:

Vision worker crash.

Yui продолжает:

- принимать текст;
- использовать LLM;
- использовать web;
- отвечать голосом.

Worker Supervisor должен перезапустить Vision отдельно.

---

# Graceful degradation

Yui всегда должна стараться выполнить запрос доступным способом.

Например:

Vision model недоступна:

```text
Vision
↓ fail
OCR
↓
partial result
```

9B не помещается:

```text
9B GPU
↓
9B CPU
```

Если auto downgrade разрешён:

```text
9B CPU
↓
4B
```

Интернет отсутствует:

```text
Web
↓ fail
local knowledge
```

---

# Расширяемость

В дальнейшем Yui должна поддерживать:

- плагины;
- MCP/tool providers;
- разные LLM engines;
- разные speech engines;
- разные vision models;
- различные устройства;
- smart-home;
- browser automation;
- IDE integration;

# Что особенно важно не испортить при дальнейшей разработке

Нельзя превращать проект в тяжёлый Electron-подобный набор процессов, где idle companion съедает гигабайты памяти без причины.

Нельзя запускать большие модели постоянно.

Нельзя отдавать scheduler право игнорировать ручной Model Lock пользователя.

Нельзя делать интернет обязательным для базового функционирования.

Нельзя использовать LLM вместо обычного кода для простых deterministic-задач.

Нельзя жертвовать FPS игры ради скорости ответа AI.

Нельзя жёстко привязывать архитектуру к конкретной версии Qwen.

# Автоматическая калибровка

При первом запуске Yui желательно провести короткий benchmark.

Например:

```text
CPU benchmark
GPU benchmark
Memory bandwidth
VRAM size
LLM 4B test
LLM 9B test
Vision test
STT test
```

После этого Yui создаёт hardware profile.

Пример:

```text
Recommended desktop:
Qwen 9B CUDA

Recommended gaming:
Qwen 4B CPU

Max safe CPU threads:
6

VRAM reserve:
3 GB
```

Это намного лучше универсальных hardcoded threshold.

# Итоговая идея продукта

Yui — это не локальный ChatGPT-клон.

Yui — это персональный AI-runtime и companion, встроенный в повседневную работу пользователя.

Он:

- слышит;
- видит;
- разговаривает;
- запоминает;
- использует инструменты;
- получает свежую информацию;
- понимает текущий контекст;
- автоматически распределяет AI-нагрузку;
- защищает производительность компьютера;
- работает локально настолько, насколько это возможно.

Главное конкурентное преимущество:

**максимально умный AI при минимально возможном влиянии на устройство пользователя.**

Архитектура должна строиться вокруг этой идеи во всех дальнейших версиях.
