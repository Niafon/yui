# Участие в разработке

## Порядок

1. Прочитайте `ARCHITECTURE.md` и `docs/decisions.md`. Многое, что выглядит
   странно, объяснено там — включая то, чего в коде намеренно нет.
2. Изменение, затрагивающее архитектурную границу, начинается с ADR в
   `docs/decisions.md`, а не с кода. Открытый вопрос закрывается решением,
   а не молчаливым выбором при реализации.
3. Требование из SRS, которое вы реализовали, добавляется в
   `docs/traceability.md` вместе со ссылкой на тест.

## Перед коммитом

```bash
make test        # go vet + go test -race, затем тесты воркеров
cd core && gofmt -l .   # должно быть пусто
```

## Правила, которые не обсуждаются

- **Данные наружу — только через `permission.FilterForProvider`.** Любой новый
  вызов провайдера проходит через фильтр категорий. Тест на утечку категории
  обязателен.
- **Политика выражается кодом, а не системным промптом.** Если правило можно
  проверить функцией — оно проверяется функцией.
- **Никакого тихого fallback.** Сбой провайдера, модели или воркера виден
  пользователю. `err` не проглатывается.
- **Инструмент объявляет уровень риска.** Значения по умолчанию «низкий» нет.
- **Опасных возможностей не добавляем.** Отправка сообщений от имени владельца,
  звонки, платежи, произвольные команды ОС и экстренный вызов — вне проекта.

## Стиль

- Go: стандартный `gofmt`, идентификаторы английские, комментарии английские.
- Python: стандартная библиотека по умолчанию; тяжёлая зависимость появляется
  только там, где без неё нет модели, и всегда с честным fallback.
- Документация и пользовательские тексты — русские.
- Комментарий объясняет **почему**, а не что. Что делает код, видно из кода.

## Контракты

Изменение `contracts/proto` — это изменение протокола: номера полей не
переиспользуются, версия протокола поднимается, несовместимый клиент получает
понятную ошибку, а не неопределённое поведение (NFR-004).
