# Архитектура реализации

Документ описывает, что именно построено, и где решения SRS превратились в код.
Расхождения с SRS перечислены в конце явно.

## Процессы

```
                    ┌──────────────────────────────────────────┐
   Android ──TLS──▶ │ yui-core (Go, один процесс)              │
   Desktop ──loop─▶ │                                          │
                    │  api  ──▶ session ──▶ agent.Runtime      │
                    │                 │                        │
                    │                 ├─▶ ContextBuilder       │
                    │                 ├─▶ permission.Engine ───┼──▶ единственный
                    │                 ├─▶ memory.Service       │    выход наружу
                    │                 ├─▶ identity.Service     │
                    │                 └─▶ inference.Manager    │
                    │                        │                  │
                    │                        └─▶ provider.Registry ─┼──▶ HTTP
                    │  scheduler   supervisor   audit          │
                    └──────┬───────────────┬──────────────────┘
                           │               │
                     store.Store     os/exec (воркеры)
                    ┌──────┴──────┐        │
             SQLite/FTS5      dev-снапшот   ▼
                                     python -m yui_worker (STT/TTS/Vision/Embeddings)
```

Внутри Go-процесса — модульный монолит (ADR-003). Ни одна ML-библиотека не
линкуется в ядро: воркеры общаются JSON-ом по loopback (SRS 18.3).

## Путь одного turn

`agent.Runtime.HandleUserTurn`:

1. `SetState(thinking)` → кадр состояния всем клиентам.
2. `ContextBuilder.Build` — собирает блоки: личность, эмоция, сводка сессии,
   последние реплики, найденные воспоминания (**по блоку на воспоминание, со
   своей категорией**), визуальное наблюдение, текущий текст.
3. `permission.Fit` — бюджет токенов; текущий текст никогда не выбрасывается.
4. `permission.FilterForProvider` — по каждому блоку решение allow/ask/deny;
   на выходе отфильтрованный контекст **и manifest** (что ушло, что нет).
   Заблокированные категории превращаются в запрос согласия владельцу.
5. `inference.Manager.Select` — если provider не зафиксирован сессией, выбирает model/backend по user policy, task complexity и telemetry; решение публикуется как `inference.decision`.
6. `LLM.Chat` — стриминг; дельты уходят в data plane сразу.
7. Как только собралось законченное предложение — `TTS.Synthesize`, аудио
   стримится параллельно с генерацией.
8. Реплики пишутся в БД, эмоция пересчитывается, аватар получает выражение.
9. Детерминированный экстрактор ищет устойчивые факты; кандидаты проходят
   проверку прав, дедупликацию по `Subject` и запись со статусом.
10. `SetState(idle)`; аудит получает запись о вызове модели с категориями.

Ошибка на любом шаге → кадр `error` и состояние `error`. Молчаливого
переключения на облако нет по построению.

## Почему так, а не иначе

**Категория как единица политики.** Разрешения написаны в терминах категорий
данных, а не таблиц. Поэтому один чувствительный факт не заставляет выбросить
весь набор воспоминаний: он выпадает один, остальное доходит.

**Один выход наружу.** Провайдеры вызываются только после
`FilterForProvider`. Это делает утечку категории (R-05) не вопросом
дисциплины, а вопросом одной функции, покрытой тестами.

**Свой WebSocket.** ~250 строк вместо зависимости. Ядро собирается и
запускается на чистой машине без сети — это прямо требуется для установки
одной командой (NFR-007) и упрощает аудит транспорта.

**Дрейф характера ограничен кодом.** `Evolve` физически не может изменить
черту больше чем на 0.05 за шаг, а `frozen` возвращает ошибку. Промпт здесь
ничего не решает (R-08).

**Ранжирование памяти — чистая функция.** `memory.Rank` не ходит в сеть и не
требует векторов: без embeddings работает лексика. Поэтому качество поиска
тестируется без моделей, а замена embedding-провайдера не ломает поведение.

## Осознанные расхождения с SRS

| Решение SRS | Что сделано | Почему |
|---|---|---|
| SQLite — основное хранилище | embedded WAL DB; dev-снапшот остаётся для unit/dev | ноль фоновых DB-процессов, один portable файл |
| Protobuf для межпроцессных контрактов | `.proto` описаны, транспорт MVP — JSON с теми же именами полей | не тянуть кодогенерацию до первых замеров; переход на gRPC не меняет воркеры |
| gRPC между Core и воркерами | JSON по loopback HTTP | «gRPC или локальный RPC» по SRS 18.3; проще отлаживать на этапе прототипов |
| Semantic retrieval | exact normalized vector cache + FTS5/BM25; ANN включается только после benchmark threshold | ADR-037 |
| Live2D | интерфейс `Avatar` + canvas-заглушка | рендерер — ресурс представления, меняется одним файлом |

## Что намеренно не реализовано

Инструменты с побочными эффектами, автоматические звонки, marketplace
плагинов, распознавание лиц. Для SEC-013 отсутствие кода — и есть выполнение
требования: инструмента экстренного вызова нет вовсе, поэтому модель не может
его вызвать.


## Изменения в архитектуре, август 2026

**Зрение перестало быть отдельной подсистемой.** Мультимодальная LLM в базовых
весах убрала из системы целый компонент: не стало второй модели, её загрузки и
выгрузки, конкуренции за VRAM и задержки первого кадра. Интерфейс `Vision`
остался неизменным — сменился только драйвер за ним. Это ровно то, ради чего
контракты провайдеров были написаны первыми.

**Диагностика стала частью модели угроз, а не отладки.** Профили процесса,
который слушает и запоминает частную жизнь, сами являются чувствительными
данными: имена функций и форма стека описывают, чем владелец занимался.
Поэтому вся отладочная поверхность привязана к loopback, выключена по
умолчанию и отвечает 404, а не 403.

**Ключевой материал теперь имеет время жизни.** Раньше DEK и производные от
пароля ключи просто оставались в памяти до сборки мусора. Теперь они
затираются сразу после использования, а под тегом `yuisecret` рантайм
дочищает копии на стеке. Это не делает систему неуязвимой к дампу памяти
работающего процесса — и в `SECURITY.md` прямо сказано, что не делает.
